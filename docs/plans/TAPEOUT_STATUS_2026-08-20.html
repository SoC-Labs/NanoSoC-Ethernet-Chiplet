Not submittable today — but the blocker is measurement, not silicon

The design's own geometric defect population is small, bounded and byte-stable at identical coordinates for nine days: 103 violations, every one of them in the power grid, none in signal routing. That is a tractable engineering problem.

What is not tractable on the current schedule is the checking. Of the six physical checks the broker requires, four have never been run against this stream at all, and the two that have both come back red.

Reproducibility is better here than in the shipping GDS

All four implementation stages — synthesis, place, CTS, route — ran at one toolkit commit and one project commit. The split-lineage defect that made the shipping stream unreproducible does not apply to this run. Three things still block a clean-clone rebuild: the tag is local-only and never pushed, the route stage carries one uncommitted patch, and eth_ss_bootrom.sv is untracked so a fresh recursive clone cannot pass the ROM gate.

“Never run” is not “clean”

Four of the eleven would return a zero that measured nothing even if executed today. Antenna has no gate area to measure — 72% of the die contains no transistor. BND is the pad-metal deck and the top cell holds 5 AP shapes on a 103-pad wire-bond die. Recording those as passes would repeat the exact failure this project has already made four times.

Three classes of problem they need different responses

Class 1 — Real design defects (103, all in the power grid)

Innovus check_drc reports 67, and every one is on a Special Wire — 62 on VDD, 8 on VSS. Not one is in signal routing. Calibre's coordinates match one-for-one. The population splits into 39 PG straps clashing with the flash-cache macro pins on an 8.4 µm pitch, 38 mesh slivers where straps meet vias and rings, and 20 single-cut vias on wide metal, plus 6 inside the vendor rf_01k memory that are not ours to fix.

The encouraging part: M4.S.2.1 is 28/28 coordinate-identical to fp1505, VIA3.R.2 23/23 identical, PO.R.8 691/691 identical. Two runs at two commits produce the same violations at the same microns. These are deterministic properties of the floorplan and PG template — a bounded, well-localised, in-flow-fixable set.

Class 2 — Artefacts of a stream with no transistors in it

PO.R.8 = 691 is the largest single number in the DRC report and it is not ours: all 691 are attributed to 22 memory and ROM macro cells whose input pins dead-end at absent standard cells. It is byte-identical on every full-chip run since 09 August — layout-independent. imec's own merged run drove the same class from 8 to 0 the moment real cell layout was imported.

Density is the inverse case, and it is real: standard-cell merge fixes M1 only. M4–M9 is roughly 4,000 core windows that no black-box merge can close. M7 fails 100% of its windows at 2.4% mean against a 10% floor. That is not marginal, and §6.5 puts density in the never-waivable class.

Class 3 — Reporting defects that make good numbers look bad and bad numbers look good

design_report.json is frozen at post-CTS because the route stage fails its gate and aborts before the report step. It therefore reads WNS +0.006 ns, 0 failing endpoints while the streamed database is −0.746 ns, 1,678 failing endpoints. The documented “source of chip numbers” describes a database superseded 66 minutes later, and looks complete. This is precisely the shape that gets mis-quoted to a broker.

Alongside it: the CI metal-fill stage sets a knob no live code reads and globs for a filename the toolkit never writes, so it burns an hour of licence and records unverified; and six ladder stages point at a GDS path that does not exist.

What the broker has actually seen and the zero that misled us

A correction to the standing assumption: a preliminary GDS was delivered, twice. The seat is booked under project TMWB45_10042. Both returns graded the same 10 August stream, md5 7f621496…, and neither touches the current lineage.

imec's CSR.R.1 = 0 is a null result, and the defect is renamed rather than absent

Their flow is fill → seal ring → DRC. The TSMC deck derives EMPTY_AREA from CHIP NOT INTERACT SR_EDGE, and every one of the 162 CSR.R.1 subrules is EMPTY_AREA AND <layer>. With a seal ring present the region collapses and the whole family becomes vacuous. Our own Calibre run on TSMC's seal-ring cell proves it: 162 subrules, 0 nonzero. They also reported zero on a stream we measure at 56.

In their filled output the same physical defect surfaces as 4,814 results across 16 subrules of the CSR.R.2/R.3/S/EN and SR.* families, 100% localised to the four die corners by coordinate test, two of them saturated at the 1000 cap. Controls confirm the test discriminates. Any future imec green must be read on those families, never on CSR.R.1.

The question that decides the schedule has not been asked

Both spent broker loops were wasted on library-replacement errors. Nothing on file tells us how long the import-and-decks loop takes, or what the cut-off is for a revised stream. That single answer determines whether 1 September is reachable, and it costs nothing to ask today.

Critical path to 1 September dependency-ordered

  1. Send the broker mail

    Lead with turnaround and cut-off date, then request a re-run with the pad library from the cup branch plus the missing plots/ images that made both prior loops unusable. Ask for the waiver template and locate the Design Delivery Form — no copy of it exists on this host, and it carries the FTP instructions.

    Cost one email · Blocks everything downstream · Needs David

  2. Re-stream from a commit that carries the padring fix

    Commit 7581af0 lands one PVDD2POC per domain but is seven hours younger than the run's launch point and is not an ancestor of it. Sending the current stream spends a broker loop reproducing a defect already fixed in source.

    Cost ~4 h of Innovus · Fixes the one hard padring error · Also clears a dirty tag

  3. Fix the PG mesh in the same re-run

    All 103 geometric violations and all 60 connectivity opens are one problem. Re-enable the macro-PG census — it was explicitly disabled at launch — add a routing halo over the flash-cache block, and repair the strap-to-ring stitch. This is the only genuine design fix on the list, and 97 of the 103 are ours.

    Cost folded into the same run · Removes the largest real defect class

  4. Decide fill ownership, then act on it

    Density is short by a wide margin and someone must fill. Delegation is currently unavailable — §7.1 conditions it on a design clean but for fill-solvable violations, and we carry 149 that are not. Either self-fill with the corner keep-out engaged, or ship BLOCKAGEFILL map rows so a foundry filler can see the keep-out at all. Today it is an in-tool object that streams nowhere.

    Cost 54 s of tool time, or five edits · Needs a decision, not more analysis

  5. Run the four checks that have never been pointed at this stream

    ERC, BND at imec's own deck revision and pitch, antenna, and LVS via lvs-batch. Three of the four decks are already on this host — including the exact wire-bond deck we previously recorded as missing. Expect antenna and BND to come back structurally empty; that must be recorded as unmeasured, not banked as a pass.

    Cost ~1 day of licence time · Two are licence-free and take minutes

  6. Close the equivalence chain on the shipping netlist

    Run lec-gate and lec-pnr against the stream being submitted, and diagnose why the RTL→gate leg dies on its twenty-first sub-compare. The work/fv model needed for that leg has been archived today at 5.6 MB so a clean cannot destroy it.

    Cost two Conformal seats, ~6 h each · Both legs are fixture-proven and automated

  7. Repoint the audit trail before anyone reads it

    signoff.yaml hardcodes fp1505 in 116 places, so running the driver unmodified grades the old build. Move design-report ahead of the gate assertion so it stops reporting CTS numbers as final, and add the Calibre summaries to what the submission bundle collects — they currently live outside its scope.

    Cost half a day · Blocks confidence, not submission

Decisions that are yours not resolvable from the code

Q1 Do we send an updated preliminary GDS, and from which commit?

The guideline date was 18 August; the hard date is 1 September, so we are two days past a guideline and twelve inside the deadline. The preliminary loop is the only mechanism that produces real cell geometry and a TSMC-side dry run. Recommendation: yes, but re-stream first — a third wasted loop is the schedule risk, not the date.

Q2 Who runs the metal fill?

Self-fill costs about 0.19 ns of unrecovered setup and 24% stream growth, and has never been executed with the corner keep-out that now exists. Delegation needs a precondition we do not currently meet. Either way the corner marker should ship, because it is nearly free and needed in both worlds.

Q3 Does boundary scan go in?

It works — 7/7, 5,063 checks, 76 bits shifted through real mapped cells with the core held in reset — and it is absent from this stream by a launch point chosen two minutes before the first bscan commit. It is the only instrument that gives pin-continuity testing with a dead core, and there is no internal scan chain to fall back on. Adding it means re-running from a bscan-bearing commit.

Q4 Is a timing signoff statement required for this submission?

The foundry manual contains zero timing requirements — setup, hold and WNS return no hits, against density, seal ring and antenna as live controls. If no statement is needed, the −0.746 ns post-route figure is a project-quality question rather than a submission blocker, and the missing setup-optimisation pass can wait behind the physical work.
